# 修改紀錄：修復口說對話「AI 轉錄文字」未顯示

- **修改日期**：2026-08-26
- **修改者**：jasonjss
- **修改目的**：口說對話進行中，狀態列只有「AI 準備先開場...」「AI 回覆中...」等動作訊息，對話視窗完全沒有顯示 AI 的轉錄文字。

---

## 一、問題描述

- 狀態列（`emitStatus`）正常顯示「AI 準備先開場...」「AI 回覆中...」等動作。
- 對話視窗（`emitLog('ai', ...)`）完全沒有出現任何 AI 轉錄文字。

## 二、根因分析

`speakingLive.js` 的連線設定原本是：

```js
responseModalities: [Modality.AUDIO],   // 純音訊模式
```

在**純音訊模式**下，Gemini live 的 `modelTurn.parts` 只會回傳音訊（`inlineData`），**不會附帶文字轉錄（`text` part）**。因此 `onmessage` 中的：

```js
const textPart = parts.find(p => typeof p?.text === 'string' && p.text.trim());
if (textPart?.text) emitLog('ai', textPart.text);   // ← 永遠找不到 text，不會執行
```

永遠找不到 `text` part，對話視窗自然沒有任何轉錄文字；狀態列的動作訊息（`emitStatus`）不受影響，所以只看到「AI 動作」而沒有內容。

## 三、修改內容

### `assets/js/speakingLive.js`

**1. 回應模式改為同時請求文字與音訊（第 191 行）**

```js
// 修改前
responseModalities: [Modality.AUDIO],
// 修改後
responseModalities: [Modality.TEXT, Modality.AUDIO],
```

如此 Gemini live 在音訊之外，會一併回傳該段語音的**文字轉錄**，程式即可透過原有的 `textPart` 邏輯顯示。

**2. 暫時加入 debug 輸出（onmessage 內）**

```js
console.log('[speakingLive] modelTurn parts:', parts.map(p => ...));
```

印出每個 part 的類型（`text` / `audio`）與文字前 30 字元，用於測試時確認：
- 轉錄是否真的有回傳
- 文字是「一次完整轉錄」還是「逐句增量」——若是逐句增量，需再套用「累積至 turnComplete 再顯示」的邏輯，避免顯示片段或重複。

> 此行為暫時性，確認轉錄結構後應移除。

## 四、驗證方式

1. `node --check assets/js/speakingLive.js` 語法檢查通過。
2. 實際開始口說對話，開啟瀏覽器 DevTools 的 Console：
   - 應看到 `[speakingLive] modelTurn parts:` 輸出，內容包含 `text:...` 與 `audio:...`。
   - 若出現 `text:` 代表轉錄已回傳，對話視窗應顯示 AI 講話內容。
   - 若仍只有 `audio:`，代表該模型/設定下不提供轉錄，需再研究其他取得轉錄的方式。

## 五、補充：TEXT + AUDIO 組合不被模型支援（已還原）

測試後回報錯誤：

```
口說已停止: The requested combination of response modalities (AUDIO, TEXT) is not supported by the model. models/gemini-2.5-flash-native-audio-latest
```

**結論**：`gemini-2.5-flash-native-audio-latest` 官方限制**只能使用純音訊（AUDIO）輸出**，不支援同時回傳文字轉錄。

**後續處置**：

1. 已將 `responseModalities` 還原為 `[Modality.AUDIO]`。
2. 已移除 onmessage 中的暫時 debug 輸出。
3. 口說對話恢復可正常使用（含先前麥克風檢查與資源清理兩項修復）。
4. 因此「AI 轉錄文字」在此模型上**無法取得**，對話視窗不會顯示 AI 逐字稿屬預期行為；目前僅顯示「AI 準備先開場...」「AI 回覆中...」等狀態動作。

**未來可行方向**（待評估，尚未實作）：

- 在對話視窗加入「（AI 語音回覆）」佔位記錄，讓使用者知道該輪是語音內容。
- 若 Google 日後開放該模型文字+音訊組合或提供轉錄功能，再恢復轉錄顯示。

## 六、最終方案：啟用 audioTranscriptionConfig 語音轉錄（2026-08-26）

經查證 `@google/genai` SDK 2.19.0 的型別定義（`LiveServerContent`），Live API 原生支援語音轉錄：

| 欄位 | 用途 |
| --- | --- |
| `serverContent.outputTranscription.text` | AI 語音的文字轉錄 |
| `serverContent.inputTranscription.text` | 使用者語音的文字轉錄 |
| `serverContent.interimInputTranscription` | 使用者說話時的即時低延遲轉錄 |
| `Transcription.finished` | 轉錄是否結束 |

**實作方式**（`speakingLive.js`）：

1. `LiveConnectConfig` 加入 `audioTranscriptionConfig: {}`（維持 `responseModalities: [Modality.AUDIO]` 不變，避免 TEXT+AUDIO 不被支援的問題）。

2. `onmessage` 中讀取轉錄並顯示：
   - `inputTranscription.text` → `emitLog('user', ...)`（對話視窗顯示 USER 列）
   - `outputTranscription.text` → `emitLog('ai', ...)`（對話視窗顯示 AI 列）
   - 保留原有的 `modelTurn.parts[].text` 處理（兩者並存，收到哪個就顯示哪個）。

**注意事項（待測試確認）**：

- 轉錄文字與 modelTurn 的送達順序彼此獨立（官方註解），可能需要觀察是否出現重複或片段顯示。
- 若同一段轉錄會重複送達，需以 `Transcription.finished` 或累積緩衝區去重。
- 使用者語音目前原本就沒有文字顯示，`inputTranscription` 一併補上了 USER 列的轉錄。

## 七、修正：啟用欄位應為 outputAudioTranscription（2026-08-26）

**第一次實作失敗原因**：加的是 `audioTranscriptionConfig`，但查證 `LiveConnectConfig` 型別定義後確認——**正確欄位是 `outputAudioTranscription` / `inputAudioTranscription`**（camelCase，對應 Python SDK 的 `output_audio_transcription` / `input_audio_transcription`）。`audioTranscriptionConfig` 不屬於 `LiveConnectConfig`，JS SDK 會忽略，故無作用。

**修正內容**（`speakingLive.js` 的 `LiveConnectConfig`）：

```js
responseModalities: [Modality.AUDIO],   // 維持純音訊（此模型不支援 TEXT+AUDIO）
outputAudioTranscription: {},           // 啟用 AI 語音轉錄（輸出側）
inputAudioTranscription: {},            // 啟用使用者語音轉錄（輸入側）
```

**接收端維持不變**（先前已正確）：`message.serverContent.outputTranscription.text` → AI 列；`message.serverContent.inputTranscription.text` → USER 列。

**待測試確認**：
- 轉錄文字是否正常出現於對話視窗。
- 若出現重複或片段，再依 `Transcription.finished` 去重或累積。

## 八、改善：增量轉錄改為收集完整句子再顯示（2026-08-26）

**問題**：轉錄文字正常出現，但 Gemini 以「增量片段」送達（一次可能只送一個單字），原本每收到一段就 `emitLog` 一列，導致對話視窗行數爆炸。

**修改**（`speakingLive.js`）：

1. 新增轉錄緩衝變數 `aiTurnBuffer` / `userTurnBuffer`。
2. `appendTranscriptChunk(buffer, text)`：片段累積時自動處理空格（新片段若以標點開頭則直接相接）。
3. `flushTranscriptBuffer(role)`：把累積的完整句子一次 `emitLog` 出去並清空。
4. `onmessage` 中：收到 `outputTranscription.text` / `inputTranscription.text` 先累積，**等 `Transcription.finished === true` 送達時**才 flush 顯示。
5. `interrupted`（被打斷）與 `stopSpeakingSession()`：將殘餘緩衝 flush 出去，避免遺失與跨會話殘留。

**預期效果**：AI 一句話只會顯示一列（而不是一個單字一列）。

## 九、調整：AI 角色標籤改為「AI 說：」（2026-08-26）

**修改**：

## 十、修正：finished 標記單獨送達導致轉錄不顯示（2026-08-26）

**問題**：AI 轉錄又完全沒有顯示。

**根因**：原本的判斷是 `if (sc?.outputTranscription?.text) { ... if (finished) flush }`——**只有「帶文字片段」的訊息才會檢查 `finished`**。但 `finished: true` 實際上是以**獨立訊息**送達（`outputTranscription` 物件只有 `finished`、沒有 `text`），因此永遠不會進入該分支，緩衝永遠不沖出。

**修改**（`speakingLive.js` 的 `onmessage`）：

1. 判斷改為 `if (sc?.outputTranscription)`（只要轉錄物件存在就處理），text 累積與 finished 檢查**分開判斷**：

```js
if (sc?.outputTranscription) {
    if (sc.outputTranscription.text) {
        aiTurnBuffer = appendTranscriptChunk(aiTurnBuffer, sc.outputTranscription.text);
    }
    if (sc.outputTranscription.finished) flushTranscriptBuffer('ai');
}
```

2. `turnComplete` 時增加備案：即使 `finished` 一直沒送達，回合結束也會把累積的轉錄沖出顯示。

## 十一、修正：「AI 說：」未生效——Service Worker 舊版快取（2026-08-26）

**問題**：轉錄有顯示，但角色標籤仍是「AI」，不是「AI 說：」。

**根因**：`sw.js` 對 script/style 請求採用 **stale-while-revalidate** 策略（先回傳快取舊版，背景再更新快取）。由於先前數輪修改都沒有 bump 快取版本，瀏覽器持續使用舊版 `speakingLogView.js` / `zh-TW.js`。

**修改**（依 CLAUDE.md 記載的快取慣例）：

1. `sw.js`：`CACHE_NAME` 由 `toeic-tutor-static-v4` 升級為 `v5`（install 時會刪除舊快取並重新快取全部最新靜態資源）。
2. `version.json`：版本由 1.4.1 升級為 1.4.1.1，並記錄本次變更（同時驅動 index.html 載入參數與更新通知）。

**使用者操作**：重新整理頁面，依更新通知（若有）重新載入；若仍顯示舊版，請硬重新整理（Cmd/Ctrl + Shift + R）或無痕視窗確認。

**問題**：所有 AI 回應（含原本 modelTurn 文字）都顯示「AI 說：」，但需求是**只有語音轉錄**用「AI 說：」。
